# ☁ Cloudy VPS · v1.0-dev

**FREE BETA 2026 · English Discord UI · Python + Docker · one dedicated node**

Начни с **START_HERE_RU.md**. Это исходный проект для запуска на собственном разрешённом Linux-хосте,
а не услуга бесплатного хостинга. Подписка и ресурсы провайдера оплачиваются/ограничиваются отдельно.

## Возможности

- `$deploy` только в настроенном канале `#deploy`: выбор **Ubuntu 22.04 LTS**, затем Launch VPS.
- Анимированный индикатор ожидания с этапами настоящей Docker-операции — без поддельных процентов.
- `$manage`: состояние, квоты RAM/CPU/диска, uptime контейнера, срок аренды, расход ресурсов.
- **Start / Stop / sshx · DM / Stats / Refresh / Reinstall**. Кнопки проверяют владельца и работают после рестарта бота.
- Reinstall требует отдельного подтверждения, удаляет весь записываемый слой, сохраняет срок окончания.
- sshx-ссылка **никогда не отправляется в канал, даже при ошибке ЛС**. ЛС проверяются до создания сеанса.
- `$status`: зелёный Operational, жёлтый High load / limited capacity, красный Incident; цвет продублирован текстом.
- SQLite/WAL, один VPS на пользователя, роль допуска, ограничения частоты и резервирование без перепродажи одной мощности.
- Квоты cgroups: **15 GiB RAM**, **3 vCPU**, без дополнительного swap; **75 GiB writable layer** через XFS project quota.
- Через 30 дней контейнер останавливается. Независимый systemd-таймер контролирует это даже без Discord-бота.
  Данные хранятся ещё 72 часа и затем удаляются работающим ботом. После удаления освобождается слот.

## Ограничения, о которых нельзя умолчать

- Контейнеры разделяют ядро хоста. **Это не полноценные VPS/VM и не безопасная публичная multi-tenant платформа.**
  По умолчанию нужен allowlist через роль; используй для доверенных тестировщиков. Для неизвестных клиентов нужны
  отдельные VM/microVM, аудит и дополнительные меры изоляции. См. `docs/SECURITY.md`.
- Нет собственного публичного IP, проброса портов, systemd внутри гостя, nested Docker, KVM и гарантированных физических CPU.
- Разрешены исходящие HTTP/HTTPS и DNS к указанным резолверам. Приватные сети/metadata и входящие соединения блокируются.
  Инструменты, которым нужны другие порты (например, обычный исходящий SSH:22), не заработают без сознательной смены политики.
- Квота диска относится к записываемому слою; базовый образ/логи/служебные файлы требуют дополнительного места хоста.
  `/run` и `/dev/shm` — ограниченные tmpfs, учитываемые в памяти. Не подменяем quota строкой в embed.
- CPU/RAM берутся из Docker stats, uptime — из Docker StartedAt. Disk — `df` гостевого root filesystem;
  это показание гостя, а не доверенная телеметрия против злонамеренного root. Если данных нет, показано Not available, а не выдуманное значение.
- Нельзя программно поменять шрифт клиента Discord. Используются обычные читаемые заголовки, жирный и моноширинный текст.
- `$status` измеряет эту ноду, не весь Freestyle и не внешнюю доступность бота. Если сам бот/VM отключён,
  бот не сможет отправить красный статус — нужен отдельный внешний мониторинг.

## 1. Настрой Discord

1. Создай приложение/бота на https://discord.com/developers/applications и **перевыпусти раскрытый токен**.
2. На вкладке Bot включи **Message Content Intent**. Members/Presence intents не требуются.
3. В OAuth2 URL Generator выбери scope `bot`, права: **View Channels, Send Messages, Embed Links, Read Message History**.
   Не выдавай Administrator. Пригласи бота только на свой сервер.
4. Создай `#deploy` и роль, например **Beta Tester**. Включи Developer Mode в Discord → Copy ID:
   сервер, канал, роль. Выдай роль только доверенным тестировщикам.
5. Для получения sshx пользователи должны разрешить личные сообщения от участников этого сервера.
6. Имя **Cloudy VPS v1.0-dev** задай в Developer Portal/профиле приложения.

## 2. Подготовь свежую выделенную Ubuntu VM

Требуется Ubuntu 22.04/24.04 хоста, Python 3.10+, Docker Engine, systemd, IPv4/IPv6 iptables,
cgroups и XFS project quotas. Хост и бот находятся **на одной VM**. Docker API по TCP не поддерживается.
Не запускай этот управляющий процесс внутри ограниченного PaaS/web-deploy или ещё одного обычного Docker-контейнера:
проверки памяти/диска должны видеть реальный хост.

Рекомендуемая стартовая конфигурация для одного гостя: **4 vCPU / 20 GiB RAM / 128 GiB disk**.
Значения по умолчанию резервируют хосту минимум 1 CPU, 2 GiB RAM и 10 GiB Docker storage.
На маленьком сервере бот покажет 0 слотов, а не выдаст несуществующие ресурсы.

Установи Docker Engine по официальной инструкции: https://docs.docker.com/engine/install/ubuntu/
В актуальном Freestyle base snapshot Docker уже установлен; проверь `docker info`.
**Не используй существующую рабочую Docker-ноду:** проект намеренно откажется выдавать VPS при обнаружении посторонних контейнеров.

Размести содержимое архива в `/opt/cloudy-vps` (либо клонируй туда свой GitHub-репозиторий **без .env**):

```bash
cd /opt/cloudy-vps
sudo cp .env.example .env
sudo chmod 600 .env
sudo nano .env
```

Заполни token/IDs. Не меняй большой план на маленький молча: если уменьшишь значения для своего теста,
интерфейс честно покажет именно новые лимиты.

## 3. Настрой настоящий лимит диска

Простой `docker run --memory ...` **не ограничивает диск**. `storage_opt size` поддерживается здесь
только через `overlay2` + XFS, смонтированный с `pquota`.
Современный Docker может по умолчанию использовать containerd `overlayfs`; установщик явно переключает свежую ноду.

**Только на свежей VM:**

```bash
cd /opt/cloudy-vps
sudo bash scripts/prepare-storage.sh --fresh-dedicated-node 100
```

Скрипт проверяет отсутствие контейнеров/образов и свободное место, полностью выделяет 100 GiB файл,
создаёт XFS, монтирует `/srv/cloudy-docker`, добавляет mount в fstab и настраивает Docker data-root.
Он **не использует sparse/truncate как обход квот**. Если ресурсов или поддержки loop/XFS нет — завершится ошибкой.
Docker daemon получает зависимость от mount, чтобы не записать данные случайно на корневой раздел.
Существующие Docker storage-настройки не перезаписываются безусловно.

Если у тебя уже есть отдельный XFS-диск, администратор может настроить `overlay2`/`pquota` вручную вместо этого скрипта.
`doctor.py` проверит реальную возможность создать контейнер с квотой. Не удаляй эту проверку.

## 4. Установи и запусти

```bash
cd /opt/cloudy-vps
sudo bash scripts/install.sh
sudo systemctl status cloudy-vps --no-pager
sudo journalctl -u cloudy-vps -n 80 --no-pager
```

Установка один раз собирает настоящий sshx 0.4.1 из закреплённого исходного релиза с Cargo.lock,
создаёт образ Ubuntu, настраивает firewall и независимый таймер окончания срока.
Для установки требуются сеть, CPU и место; последующие выдачи используют готовый образ, а не пересобирают его.
Из-за особенностей хоста/версий зависимостей Docker build нужно подтвердить на твоём сервере.

Команды в Discord:

```text
#deploy: $deploy → Ubuntu 22.04 → Launch VPS
$manage
$status
$help
```

Управляющий бот перезапускается через systemd; после рестарта хоста гости **не стартуют автоматически**,
чтобы не запустить истёкшие контейнеры. Владелец запускает действующий VPS через Start.
Если Docker был остановлен административно, после его восстановления проверь и при необходимости запусти `cloudy-vps`.

## Freestyle

Открой **docs/FREESTYLE_RU.md**. Есть необязательный TypeScript/Node SDK bootstrap для создания **одной новой** VM.
Сам бот остаётся Python. API-ключ Freestyle нужен только твоему локальному bootstrap и не нужен runtime-боту.
Скрипт не запускался в твоём аккаунте и не использует ключи из чата.

## Обслуживание

```bash
sudo -u cloudy bash -c 'cd /opt/cloudy-vps && .venv/bin/python scripts/doctor.py'
sudo systemctl restart cloudy-vps
sudo systemctl list-timers cloudy-expiry.timer
sudo docker ps --filter label=io.cloudy.managed=true
```

Не выводи `cat .env`, Docker exec terminal logs или sshx URL в публичные логи.
Нужные сообщения бота содержат только тип ошибки/код, не сырые ответы Docker/HTTP.
SQLite и Docker root нужно резервировать согласованно: останови бот и гостей перед консистентным snapshot/backup.
Не копируй работающий SQLite WAL только одним `.sqlite3`-файлом; используй SQLite backup API либо остановку сервиса.
Снимки VM могут содержать `.env` и приватные данные: не публикуй их и не клонируй публично.

Обновление кода: останови `cloudy-vps`, сохрани приватную резервную копию, обнови исходники/зависимости,
перезапусти только сервис. **Не запускай prepare-storage.sh повторно.** Обновление гостевого образа применяется
только к новым контейнерам/подтверждённым переустановкам; активные файловые системы не подменяются автоматически.

## Частые ошибки

| Ошибка | Что сделать |
|---|---|
| Бот молчит | Новый token, Message Content Intent, правильный GUILD_ID и права канала |
| No capacity | Добавь настоящие RAM/CPU/disk; остановленные гости всё ещё держат резерв |
| quota_backend / quota_probe_failed | Нужен overlay2/XFS/pquota, а не обычный overlayfs/ext4 |
| firewall_not_ready | `systemctl status cloudy-firewall`; проверь sudo check, iptables/IPv6 и DOCKER-USER |
| untracked_container | Проверь контейнеры вручную; не удаляй чужие данные. Нода должна быть выделенной |
| node_not_ready | Дождись reconcile; проверь ошибки обслуживания и доступ к Docker |
| sshx_timeout | Проверь сборку sshx и исходящий HTTPS:443; публичная ссылка при ошибке не выдаётся |
| Could not deliver private session | Разреши DMs; бот не публикует резервную ссылку в канале |

## GitHub и тестирование

```bash
python3 -m unittest discover -s tests -v
python3 scripts/check-secrets.py
python3 -m compileall -q cloudy scripts tests
```

CI запускает проверки, но **никогда не размещает бота/sshx/VPS на GitHub Actions**.
Secret check — дополнительная простая проверка; это не гарантия отсутствия всех возможных секретов.
Не отключай GitHub push protection. Если секрет уже попал в git history, сначала отзови его,
затем очисти историю по официальным инструкциям GitHub.

Зависимости Python ограничены совместимыми major-версиями, но lockfile с проверенными сборками не приложен,
потому что сеть установки недоступна в среде сборки. После успешной установки сохрани свой `pip freeze` для воспроизводимости.
Freestyle SDK устанавливается актуальный по официальному quickstart; API/bootstrap обязательно проверь на своём плане.

Подробнее: `docs/SECURITY.md`, `docs/TEST_REPORT.md`, `docs/SOURCES.md`, `docs/ui-preview.html`.
Preview — отдельный образец оформления с демонстрационными значениями, не статус живого сервера.
